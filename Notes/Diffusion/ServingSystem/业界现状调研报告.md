# 面对混合负载的高效 DiT 推理服务系统 —— 业界现状调研报告

## 一、研究背景与问题

近年来，扩散模型已成为生成式人工智能的重要技术路线，其中基于 Transformer 结构的扩散模型（Diffusion Transformer, DiT）凭借良好的可扩展性与建模能力，逐步取代传统 U-Net 结构，成为图像、视频及多模态生成等在线服务中的主流推理架构[1]。在实际业务部署中，DiT 推理通常以在线服务形式运行，需要持续处理来自不同用户的生成请求。这类请求在多个维度上呈现出显著的动态性与异构性特征：请求到达时间不可预测，且在分辨率、时序长度与去噪步数等配置上高度异构，导致不同请求在计算量与显存占用上的开销差异显著。在同一推理实例中，系统往往需要同时处理低分辨率的短请求与高分辨率、多时长的长请求。从计算结构上看，DiT 推理由多步去噪构成，其中去噪阶段占据主要计算与显存开销，是系统吞吐与资源利用率的关键瓶颈，因此，在在线混合负载场景下高效执行去噪阶段，是 DiT 推理系统性能优化的核心问题之一。

然而，现有系统如 XDiT[1] 等通常以请求为最小执行单位，去噪阶段不可中断，在在线混合负载场景下显著限制系统并发度与加速器算力利用率。为缓解传统 DiT 推理系统在并发度与吞吐方面的限制，近期研究开始从推理流程结构入手，对扩散模型的在线服务架构进行系统级优化。TridentServe[2] 是其中具有代表性的工作，其将扩散推理流程拆分为编码、去噪与解码三个阶段，并基于各阶段计算与资源需求差异，引入阶段级调度与静态批处理机制，从而在单实例内支持多请求交错执行，缓解请求级串行执行带来的吞吐瓶颈。实验结果表明，在离线或请求配置相对一致的场景下，阶段级解耦能够显著提升去噪阶段的批处理效率，从而提高系统整体吞吐能力。

然而，在真实在线服务场景中，请求到达时间与配置参数高度动态且异构，使阶段级批处理机会呈现碎片化特征。当请求无法在到达时间或配置上对齐时，TridentServe 所采用的静态批处理策略难以持续生效，系统整体吞吐能力仍然受限，去噪阶段依旧是制约性能提升的关键瓶颈。随着在线推理负载中请求到达时间与配置参数的动态性不断增强，现有 DiT 推理系统以"请求"为最小执行单元、去噪阶段不可中断的执行粒度，逐渐成为制约系统并发度与吞吐能力扩展的关键因素。在混合负载场景下，即使系统中存在大量短请求或后续到达的请求，也只能在队列中等待，难以充分利用计算资源。

从执行模型角度看，扩散模型逐步去噪的结构为去噪步级调度提供了可能。通过在去噪过程中对不同请求进行交错执行，使长请求为短请求让出部分执行机会，系统有望借助更灵活的批处理方式提升计算资源利用率。然而，这一思路的落地并不仅是调度策略的调整，而是直接涉及请求上下文管理与显存组织方式等更为核心的系统问题。在高并发在线 DiT 推理场景中，请求到达时间与配置参数呈现出高度动态且显著异构的特征，不同请求在分辨率、序列长度与剩余去噪步数上差异巨大。为提升系统吞吐能力，推理系统不可避免地需要采用连续批处理（continuous batching），将不同到达时刻、不同配置的请求动态组合执行，以持续填充去噪阶段的计算资源。

然而，在去噪步级调度与抢占下，请求上下文在显存中的生命周期与占用规模随批次动态变化。单个 DiT 请求需维护跨多个去噪步存活的中间状态，其显存占用随分辨率与序列长度迅速增长至 GB 级别[3]。若仍采用按请求连续分配或粗粒度管理的显存策略，连续批处理将直接放大显存碎片化问题，使系统并发能力受限于可驻留请求上下文数量，而非加速器的实际显存容量。同时，在混合分辨率与混合步数的在线场景中，不同请求的单步计算开销差异显著，传统批处理调度基于固定请求数量的调度方式难以刻画真实计算成本，也难以为基于服务质量目标（SLO）的调度决策提供可靠依据。在缺乏统一成本度量与稳定上下文管理机制的情况下，批处理策略难以持续生效，甚至可能进一步恶化系统吞吐表现。

综上所述，在高并发在线 DiT 推理场景中，系统吞吐能力的提升不仅依赖于调度粒度的细化，更首先受制于请求上下文在显存中的高效组织与管理方式。只有在显存层面能够稳定承载大量动态请求上下文的前提下，去噪步级调度与批处理机制才能真正发挥作用。

## 二、现有工作分析

### 2.1 批处理优化：DiT-Serve

DiT-Serve[4] 是首个将视频和图像生成作为服务跨用户应用集成的系统，其核心贡献在于提出 Step-Level Batching（步级批处理）和 Brick Attention（砖块注意力）两项关键技术。Step-Level Batching 借鉴了 LLM 服务中的连续批处理思想，在每个去噪步结束后，调度器可以选择将已完成的请求移出，将新的高优先级请求注入，从而消除 GPU 空闲周期，最大化利用率。Brick Attention 则解决了序列并行中的 padding 浪费问题，通过为每个请求分配大小合适的 GPU 环（如 1、2、4、8 GPU 的环），避免了将所有序列填充到最长长度的问题。此外，DiT-Serve 引入了 SRPTF（最短剩余处理时间优先）调度策略，动态版本的最短作业优先，每次调度决策时都要重新计算剩余工作量，从而降低平均完成时间和尾部延迟。

实验结果表明，DiT-Serve 在三个 SOTA 视频扩散模型（Open-Sora、Mochi、CogVideoX）上实现了吞吐量提升 2-3×，平均延迟降低 3-4×，尾部延迟（P95/P99）显著降低的效果。然而，DiT-Serve 也存在一定局限性：步级批处理需要在每个去噪步结束后进行调度决策，增加了控制开销；频繁的请求切换可能导致上下文切换开销；Brick Attention 实现复杂，需要精细的 GPU 管理。此外，DiT-Serve 主要针对视频生成任务，对图像生成任务的优化有限。

### 2.2 资源分配优化：DDiT

DDiT[5] 是一个面向 Text-to-Video (T2V) 推理服务的高效资源调度系统，其核心贡献在于提出阶段间解耦（Inter-phase Decoupling）和阶段内解耦（Intra-phase Decoupling）机制。阶段间解耦通过将模型权重加载与通信组构建分离，实现了 DiT 和 VAE 的异构部署：所有 GPU 加载完整模型权重但不建立通信组，DiT 阶段开始时动态建立通信组，DiT 阶段结束后释放非 master GPU，从而避免了预定义分组带来的资源锁定。阶段内解耦则支持在 DiT 执行过程中动态调整并行度（DoP），在每个去噪步结束后，根据资源可用性动态调整 DoP，实现步骤级的资源优化。这种分离式部署的一个重要优势在于，它允许 DiT 和 VAE 这两个计算特性差异显著的组件根据各自的工作负载独立扩容或动态调整资源，避免了传统整体式部署中资源分配的"一刀切"问题。

DDiT 的实证分析揭示了 T2V 系统的四个关键洞察：第一，Batching 对 T2V 无效，DiT 和 VAE 在 batch size=1 时 GPU 利用率已接近饱和；第二，DiT 与 VAE 的并行度需求不一致，VAE 阶段所有 GPU 处理相同的输入张量，增加 GPU 只是冗余计算；第三，最优 DoP 因分辨率而异，低分辨率用高 DoP 反而因通信开销导致性能下降；第四，静态部署导致资源浪费，请求一旦开始执行就无法调整 DoP。基于这些洞察，DDiT 设计了基于饥饿时间的贪心调度算法，为每种分辨率确定一个平衡点 B（性能增益最大的 DoP 翻倍点），并在运行时动态调整资源分配。实验结果表明，DDiT 在 8×H800 上实现了 P99 延迟降低 30.4%，平均延迟降低 30%，成本达到理论最优的 1.39×。

### 2.3 阶段级资源调度：TridentServe

TridentServe[2] 首次系统性分析了扩散流水线的阶段异构性，揭示了资源需求的不对称性。通过分析 4 个主流模型（Stable Diffusion 3、Flux.1、CogVideoX、HunyuanVideo），TridentServe 发现：Encode 阶段是 Transformer 编码器，处理长度 ≤500，主要靠 batching 提效；Diffuse 阶段是 DiT 模型，处理长度 100-120k，占 70%+ 时间，计算密集，对并行度敏感；Decode 阶段是 VAE 解码器，内存密集，对并行度不敏感，增加 GPU 收益有限。此外，工作负载模式变化时，阶段间的资源比例也需要动态调整。基于这些分析，TridentServe 提出了阶段级解耦的部署方式，其重要优势之一在于允许各阶段根据工作负载独立扩容：当 DiT 阶段成为瓶颈时，系统可以单独增加 DiT 阶段的 GPU 数量，而无需复制整个管线，从而避免了资源浪费。

基于这些分析，TridentServe 提出动态 stage-level 服务范式，包含两大抽象：Placement Plan（模型部署）和 Dispatch Plan（请求调度）。Placement Plan 决定每个 GPU 上部署哪些阶段的模型副本，支持 6 种 Placement 类型（⟨EDC⟩、⟨DC⟩、⟨ED⟩、⟨D⟩、⟨E⟩、⟨C⟩），并通过 Virtual Replica 概念实现通信开销最小化的请求执行。Dispatch Plan 则为每个请求的每个阶段选择 GPU、并行策略和执行时间，通过 ILP 建模求解最大化 SLO 达标率。TridentServe 还设计了 Adjust-on-Dispatch 机制，当 Monitor 检测到阶段间速度失衡时，无停机地动态重部署模型，进一步体现了分离式架构在资源动态调整方面的灵活性。实验结果表明，TridentServe 在 4 个模型和多种工作负载下实现了平均延迟降低最高 2.5×，P95 延迟降低最高 3.6×，P99 延迟降低最高 4.1×。

### 2.4 步级并行度调整：TetriServe

TetriServe[6] 证明了 DiT 步级调度问题是 NP-hard 的，并提出了 Round-Based Scheduling（基于轮次的调度）来解决这一问题。TetriServe 的核心洞察包括：第一，DiT 工作负载输入异构但执行可预测，每个分辨率的每步运行时间高度可预测（CV < 0.7%），这使得 deadline-aware 调度成为可能；第二，序列并行的扩展效率是次线性的，且因分辨率而异，小分辨率用高并行度是浪费，大分辨率用低并行度是不够；第三，步级并行度调整可以适应 deadline，高分辨率或紧急请求分配更多 GPU，小分辨率或不紧急请求节省资源。

基于这些洞察，TetriServe 设计了 Deadline-Aware GPU Allocation 和 DP 求解装箱算法。Deadline-Aware GPU Allocation 为每个请求找到满足 deadline 的最小 GPU 分配，通过离线画像获取每种分辨率和 GPU 数量组合的执行时间，运行时查表枚举。DP 求解装箱算法则将每轮的调度问题建模为分组背包问题，用动态规划在 O(RN) 时间内求解每轮调度。此外，TetriServe 还设计了 GPU Placement Preservation（放置保持）和 Work-Conserving Elastic Scale-Up（弹性扩展）机制，减少轮次间开销，充分利用 GPU。实验结果表明，TetriServe 在 FLUX.1-dev（8×H100）和 SD3（4×A40）上实现了 SLO 达标率最高提升 32%，与缓存加速（Nirvana）正交兼容，组合使用 SAR 从 0.42 提升到 0.88。

### 2.5 流水线并行优化：DisagFusion

DisagFusion[7] 是一个解耦式扩散模型推理系统，通过异步流水线并行和弹性调度，在异构 GPU 上实现高效部署。传统流水线中，各阶段之间存在大量等待时间，DisagFusion 通过将 latent 分成多个 chunk，实现发送 chunk i 与计算 chunk i+1 重叠，并使用双缓冲（两个缓冲区交替读写）减少等待时间，从而实现通信与计算的重叠。分离式架构的核心优势之一在于允许各阶段根据工作负载独立扩容：DisagFusion 的弹性调度策略能够根据运行时负载动态调整各阶段的实例数量，当 DiT 阶段出现瓶颈时，系统可以从空闲阶段借 GPU 给瓶颈阶段，实现资源的动态优化配置。

DisagFusion 还设计了弹性实例调度策略，通过性能预测和运行时反馈动态调整各阶段的实例数。性能预测模型基于离线 profiling 获取基准数据，在线微调适应实际负载；运行时反馈则监控各阶段队列长度，检测瓶颈阶段，并从空闲阶段借 GPU 给瓶颈阶段。实验结果表明，DisagFusion 在 Stable Video Diffusion 和 OpenSora 上实现了吞吐量提升 3.4×-20.5×，延迟降低 18.5×，并支持异构 GPU 部署（如 4× A100 + 4× V100 混合配置）。

### 2.6 微服务化架构：LegoDiffusion

LegoDiffusion[8] 提出了微服务化（micro-serving）的扩散工作流推理系统，将 Text-to-Image 工作流分解为松耦合的模型执行节点，实现独立管理和调度。LegoDiffusion 的核心设计包括：编程接口与编译（Python-embedded DSL 用于组合扩散工作流，图编译器将工作流转换为 DAG）、运行时与数据平面（惰性执行、基于 NVSHMEM 的分布式数据引擎、GPU-direct 零拷贝张量移动）、工作流节点调度（模型粒度扩展、多租户模型共享、自适应并行度）。微服务化架构的核心优势在于允许各个组件根据工作负载独立扩容：当某个模型（如基础扩散模型）成为瓶颈时，系统可以单独扩展该模型的实例数量，而无需复制整个工作流，从而避免了资源浪费。

LegoDiffusion 的实证分析揭示了整体式部署的四个核心问题：L1（低效的全复制扩展），单体服务强制粗粒度复制，加载延迟增加 80%，GPU 内存浪费 75%；L2（无法共享通用模型），工作流实例严格隔离，流行模型在多个工作流中重复部署；L3（运行时低效），黑盒封装导致系统可见性缺失，无法优化数据流和执行逻辑；L4（系统脆弱性和维护开销），紧耦合导致系统脆弱，单点故障级联。基于这些分析，LegoDiffusion 实现了请求率提升 3×，突发流量容忍度提升 8×，GPU 需求减少高达 3×。

## 三、现有工作的局限性

尽管上述工作在各自关注的维度上取得了显著进展，但仍存在以下局限性。首先，大多数工作只从单一维度优化，缺乏系统级协同设计。DiT-Serve 专注于批处理优化，DDiT 专注于资源分配优化，TridentServe 专注于阶段级资源调度，TetriServe 专注于步级并行度调整，DisagFusion 专注于流水线并行优化，LegoDiffusion 专注于微服务化架构，但这些工作之间缺乏深度整合，难以实现系统整体性能最优化。

其次，现有工作缺乏统一的成本度量和资源抽象。不同工作使用不同的度量方式（如请求数量、GPU 数量、Token 数量等），难以在异构请求之间建立统一的资源视角。在混合负载场景下，不同请求在分辨率、步数、时长等维度高度异构，缺乏统一的成本度量使得调度决策难以准确反映不同请求对系统资源的真实消耗。

第三，显存管理、计算执行、调度控制三个层面缺乏协同设计。显存管理层需要保证请求上下文在抢占过程中的安全保存，计算层需要通过在线装箱最大化执行效率，调度层需要在系统负载变化时动态调整请求执行顺序，但这三个层面之间缺乏深度协同，难以实现系统整体性能最优化。

第四，大多数工作针对特定场景优化，通用性不足。DiT-Serve 主要针对视频生成任务，DDiT 主要针对 T2V 任务，TetriServe 主要针对图像生成任务，这些工作在其他场景下的适用性有限。此外，大多数工作假设同构 GPU 环境，难以利用异构 GPU 的特性。

## 四、未来研究方向

针对混合负载的高效 DiT 推理服务系统，未来研究应重点关注以下方向。首先，建立统一的成本抽象，将 DiT Token 视为统一的"成本单位"，作为系统进行显存管理、连续批处理与调度决策的基础度量，从而在异构请求之间建立统一的资源视角，为后续系统设计提供一致的抽象基础。

其次，优化显存管理机制，围绕 DiT Token 的统一抽象，研究面向去噪步级执行的请求上下文管理机制。将请求在去噪阶段产生并需要跨多个去噪步长期存活的上下文状态统一抽象为 Token 序列，并将其从逻辑上连续的请求上下文，映射为物理上离散的 HBM 显存页。通过引入分页化的显存管理方式，系统可以避免为单个请求分配大块连续显存，从根本上缓解混合分辨率、混合帧长负载下的外部显存碎片问题。

第三，充分利用分离式推理架构的优势，允许各个组件根据工作负载独立扩容或动态调整资源。分离式部署将推理流程拆分为多个独立组件（如文本编码、扩散去噪、图像解码），每个组件可以根据自身的计算特性和负载情况独立扩展，从而实现更精细的资源管理。例如，当 DiT 阶段成为瓶颈时，系统可以单独增加 DiT 阶段的 GPU 数量，而无需复制整个管线，避免了资源浪费。这种弹性资源分配机制能够显著提升系统在混合负载场景下的资源利用率和整体吞吐能力。

第四，设计基于 Token 预算的连续批处理机制，在每一个去噪步中，系统以"当前批次中所有请求的 Token 总数不超过预算"为原则，从请求队列中动态选择并装箱多个请求，构建可并行执行的批次。与传统基于请求数量或固定批处理大小的方法不同，该机制能够自然适配不同分辨率、不同剩余步数的请求，实现真正意义上的异构请求融合执行。

第五，设计面向吞吐优先场景的在线调度策略，综合考虑请求的 Token 规模、剩余去噪步数以及 SLO 约束，对请求的剩余执行成本进行近似建模，并据此设计轻量化的在线调度策略。具体而言，调度器可采用基于最短剩余时间优先的优先级策略，在满足 Token 预算与显存可用性的前提下，对请求进行准入、排序与抢占决策。

第六，实现显存管理、计算执行、调度控制三个层面的协同设计。显存管理层保证请求上下文在抢占过程中的安全保存，计算层通过在线装箱最大化执行效率，调度层在系统负载变化时动态调整请求执行顺序，避免长请求长期占用上下文资源而压制整体吞吐。三个层面协同工作，以提升整体吞吐能力为首要目标，实现面对混合负载的高效 DiT 推理服务系统。

## 五、总结

本文对扩散模型服务系统领域的现有工作进行了全面调研和分析。通过对 DiT-Serve、DDiT、TridentServe、TetriServe、DisagFusion、LegoDiffusion 等代表性工作的深入分析，本文揭示了现有工作在批处理优化、资源分配优化、阶段级资源调度、步级并行度调整、流水线并行优化、微服务化架构等维度的技术细节、优势与局限性。分离式推理架构的核心优势在于允许各个组件根据工作负载独立扩容或动态调整资源，这一特性在混合负载场景下尤为重要。基于这些分析，本文提出了统一成本抽象、显存管理优化、分离式架构的弹性资源分配、连续批处理优化、调度策略优化、协同设计等未来研究方向，为面对混合负载的高效 DiT 推理服务系统的设计与实现提供了理论基础和技术参考。
