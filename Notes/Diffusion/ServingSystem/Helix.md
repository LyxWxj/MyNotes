## 1. 论文概述

Helix 是一个面向异构 GPU 集群的 LLM 分布式推理系统。核心思想是将 LLM 推理计算建模为 **有向加权图上的最大流问题**，通过混合整数线性规划（MILP）联合优化模型放置和请求调度。

**核心贡献**：
- 将异构 GPU/网络推理建模为最大流问题
- 提出 MILP 算法联合优化模型放置和请求调度
- 在异构集群上实现 2.3× 吞吐量提升

> **注意**：虽然本文主要针对 LLM，但其异构调度思想可推广到 DiT 推理场景。

## 2. 背景与问题

### 2.1 异构 GPU 集群的挑战

现代数据中心通常包含多种 GPU 型号：

| GPU 型号 | 显存 | 计算能力 | 互联带宽 |
|---------|------|---------|---------|
| A100 80GB | 80GB | 312 TFLOPS | NVLink 600GB/s |
| V100 32GB | 32GB | 125 TFLOPS | NVLink 300GB/s |
| T4 16GB | 16GB | 65 TFLOPS | PCIe 32GB/s |

**问题**：
1. **资源异构**：不同 GPU 的计算/显存/带宽差异大
2. **网络异构**：机内 NVLink vs 机间 InfiniBand 带宽差异
3. **负载不均**：请求大小、模型规模变化大

### 2.2 现有方法的局限

1. **同构假设**：假设所有 GPU 相同，无法利用异构资源
2. **分离优化**：模型放置和请求调度独立优化，无法全局最优
3. **启发式方法**：缺乏理论保证，性能不稳定

## 3. 核心技术：最大流建模

### 3.1 图构建

将推理系统建模为有向加权图 $G = (V, E)$：

**节点（V）**：
- **GPU 节点**：每个 GPU 实例一个节点
- **源节点（s）**：表示请求到达
- **汇节点（t）**：表示请求完成

**边（E）**：
- **GPU 到 GPU**：表示数据传输，容量 = 网络带宽
- **源到 GPU**：表示请求分配，容量 = 请求到达率
- **GPU 到汇**：表示请求完成，容量 = GPU 处理能力

### 3.2 容量计算

GPU 处理能力（tokens/s）：
$$C_{gpu} = \frac{\text{计算能力 (FLOPS)}}{\text{每 token 所需 FLOPS}}$$

网络带宽：
$$C_{net} = \text{互联带宽} \times \text{利用率}$$

### 3.3 最大流求解

目标：最大化从源到汇的流量（即系统吞吐量）

$$\max \sum_{e \in E_{out}(s)} f(e)$$

约束：
- 流量守恒
- 容量约束
- GPU 显存约束

## 4. MILP 优化

### 4.1 决策变量

- $x_{i,j}$：是否将模型层 $j$ 放置在 GPU $i$
- $y_{r,i}$：是否将请求 $r$ 调度到 GPU $i$
- $f_{i,j}$：GPU $i$ 到 GPU $j$ 的流量

### 4.2 目标函数

$$\max \sum_{r \in R} \text{throughput}(r)$$

### 4.3 约束条件

1. **放置约束**：每个模型层只能在一个 GPU 上
2. **调度约束**：每个请求只能分配到包含所需模型层的 GPU
3. **容量约束**：不超过 GPU 计算/显存/网络容量
4. **依赖约束**：模型层间的依赖关系

### 4.4 求解策略

- **离线求解**：对常见配置预计算最优策略
- **在线调整**：运行时根据负载微调
- **分层求解**：将大问题分解为小子问题

## 5. 系统实现

### 5.1 架构

```
┌─────────────────────────────────────────────┐
│              Helix Controller               │
│  ┌──────────────┐  ┌──────────────────────┐│
│  │ Cluster Monitor │  │ MILP Solver       ││
│  └──────────────┘  └──────────────────────┘│
│              ↓                  ↓            │
│  ┌──────────────────────────────────────┐  │
│  │        Placement & Scheduling        │  │
│  └──────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
         ↓                    ↓
   ┌─────────┐          ┌─────────┐
   │  GPU 1  │  ←────→  │  GPU 2  │
   └─────────┘          └─────────┘
```

### 5.2 工作流程

1. **监控**：收集 GPU 利用率、网络带宽、请求队列
2. **建模**：构建当前状态的图表示
3. **求解**：MILP 求解最优放置和调度
4. **执行**：应用求解结果，迁移模型/请求

## 6. 实验结果

### 6.1 实验设置

- **集群**：8× A100 + 8× V100 + 8× T4
- **模型**：LLaMA-70B, LLaMA-13B
- **负载**：真实 trace + 合成负载

### 6.2 性能对比

| 方法 | 吞吐量 (req/s) | P99 延迟 (s) |
|------|---------------|-------------|
| FIFO + 轮询 | 12.3 | 8.2 |
| 最佳静态放置 | 18.7 | 5.4 |
| **Helix** | **28.2** | **3.1** |

### 6.3 异构优势

- **混合 GPU**：相比纯 A100 集群，混合集群成本降低 40%
- **网络感知**：利用 NVLink 高带宽，减少跨机通信
- **负载均衡**：避免热点 GPU，提高整体利用率

---

## 7. 对 DiT 推理的启示

虽然 Helix 针对 LLM，但其思想可推广到 DiT：

1. **异构调度**：DiT 模型也可在异构 GPU 上部署
2. **最大流建模**：将 DiT 推理的 pipeline 建模为图
3. **联合优化**：模型放置（DiT/VAE/Text Encoder）和请求调度

**应用场景**：
- DiT（计算密集）放在 A100
- VAE（带宽受限）放在 V100
- Text Encoder（轻量）放在 T4
