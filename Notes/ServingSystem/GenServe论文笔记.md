# GenServe: Coordinated Serving of Heterogeneous Diffusion Workloads

> 论文链接: https://arxiv.org/abs/2604.04335
> 笔记时间: 2026-06-14

---

## 一、问题背景

### 1.1 核心挑战

生产平台需要在同一 GPU 集群上同时服务 **文生图 (T2I)** 和 **文生视频 (T2V)** 请求，但两者在计算需求和延迟目标上存在巨大差异：

| 维度 | T2I (SD3.5) | T2V (Wan2.2-5B) |
|------|-------------|-----------------|
| 单步计算量 | 1× | 20× (720p) |
| 延迟要求 | 秒级 | 十秒级 |
| 去噪步数 | 20-50 | 40-50 |
| 输出 | 1 张图 | 81 帧视频 |
| 中间状态大小 | ~0.5MB | ~27MB (720p) |

### 1.2 现有方案的缺陷

| 策略 | 问题 |
|------|------|
| **FIFO** | 长视频请求阻塞图像请求，图像 SLO 满足率从 62% 暴跌至 12% |
| **SJF (最短作业优先)** | 总是优先处理图像，视频请求饥饿 |
| **SRTF (最短剩余时间)** | 无法准确估计剩余时间，且不支持抢占 |
| **静态并行度** | 无法适应不同工作负载组合 |

**核心问题：** 没有任何系统支持异构扩散模型工作负载的协调资源管理。

---

## 二、核心观察

GenServe 基于三个关键观察：

### 观察 1: 可预测的逐步执行

扩散推理的每步执行时间高度可预测（变异系数 CV < 0.05%），可以精确估计每个请求的剩余完成时间。

```
实际测量:
- SD3.5 Medium (T2I): 每步 ~39ms，CV = 0.03%
- Wan2.2-T2V-5B (T2V): 每步 ~781ms，CV = 0.04%
```

### 观察 2: 步骤边界天然可抢占

不同于 LLM 推理的不可预测输出长度，扩散推理在去噪步骤边界可以零成本暂停：
- 暂停状态仅为紧凑的 latent 张量
- 720p 视频暂停状态: 最大 27.2MB
- 暂停延迟: ≤ 4.2μs
- 恢复延迟 (SP=8, 720p): 0.868ms

### 观察 3: T2I/T2V 计算特征截然不同

| 特征 | T2I | T2V |
|------|-----|-----|
| DiT 占比 | ~95% | ~92% |
| VAE 占比 | ~5% | ~8% |
| 批处理收益 | 高 | 低 |
| 序列并行收益 | 低 | 高 |

## 三、系统架构

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    GenServe 调度器                       
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     
│  │ 抢占管理器       │ 资源分配器       │ DP 求解器

│         └────────────────┼────────────────┘             
│                          ▼                              
│  ┌─────────────────────────────────────────────────┐   
│  │              GPU 集群 (N 卡)
```

2. **抢占管理器**: 管理视频请求的暂停/恢复
3. **资源分配器**: 动态调整 SP 度数和批处理大小
4. **DP 求解器**: 联合优化调度决策

## 四、机制详解

### 4.1 机制一：智能视频抢占

#### 4.1.1 抢占原理

当图像请求到达但无可用 GPU 时，系统选择最不紧急的视频进行暂停：

```
选择函数: slack_v = D_v - t_now - S_v^rem · T_step(v)

其中:
- D_v: 视频 v 的截止时间
- t_now: 当前时间
- S_v^rem: 剩余去噪步数
- T_step(v): 每步预估时间
```

**抢占条件:** 仅选择 slack > 0 的视频（暂停不会导致其超时）

#### 4.1.2 恢复策略

视频在两种条件下恢复执行：

1. **Budget-tight**: 剩余时间低于预估完成时间
   ```
   t_now + S_v^rem · T_step(v) ≥ D_v - ε
   ```

2. **Idle**: 持续无新图像请求到达
   ```
   空闲时间 > threshold_idle
   ```

#### 4.1.3 抢占开销

| 操作 | 延迟 | 内存 |
|------|------|------|
| 暂停 | ≤ 4.2μs | 最大 27.2MB (720p) |
| 恢复 (SP=1) | 0.109ms | - |
| 恢复 (SP=8, 720p) | 0.868ms | - |

---

### 4.2 机制二：弹性资源分配

#### 4.2.1 弹性序列并行度 (SP)

DiT 阶段（占总运行时间 92-95%）通过多 GPU 序列并行加速，VAE 阶段始终在单 GPU 执行。

**动态 SP 调整:**
- GPU 紧张时: 降低 SP 度数，释放 GPU 给其他请求
- GPU 空闲时: 提高 SP 度数，加速视频生成

```
SP 调整示例:
┌──────────┐     ┌──────────┐     ┌──────────┐
│ SP=8     │ ──▶ │ SP=4     │ ──▶ │ SP=8     │
│ 8 GPU    │     │ 4 GPU    │     │ 8 GPU    │
│ 快速推理 │     │ 释放 4 卡│     │ 恢复加速 │
└──────────┘     └──────────┘     └──────────┘
```

**SP 重配置开销:**
- 频率: < 0.4% 总去噪步骤
- 延迟: 与恢复延迟相同

#### 4.2.2 SLO 感知动态批处理

同分辨率图像请求可合并批处理以提升吞吐：

```
批处理决策流程:
1. 收集等待队列中的同分辨率图像请求
2. 查询 Profiler 预测扩大批次后的延迟
3. 验证所有请求仍能满足截止期
4. 基于最早截止期动态计算等待预算
5. 决定批次大小
```

**批处理收益:**
- 图像请求吞吐提升: 2-4×
- 对视频请求无影响

---

### 4.3 机制三：SLO 感知在线调度器

#### 4.3.1 问题建模

将联合资源分配建模为背包问题：

```
目标: max Σ z_r（最大化满足截止期的请求数量）

约束: Σ|X_r(t+Δ_round)| ≤ N（GPU 容量约束）

其中:
- z_r: 请求 r 是否满足截止期 (0/1)
- X_r(t+Δ_round): 请求 r 在下一轮次的资源分配
- N: GPU 总数
```

#### 4.3.2 DP 求解算法

算法分三阶段：

**阶段 1: 构建评分候选**
- 图像: 构建预算化 EDF 批次候选
- 视频: 生成少量锚定候选（保持、继续、升降 SP、恢复）

**阶段 2: 背包 DP**
```
DP 状态: dp[g][n] = (可恢复数, 累积效用分)
其中:
- g: 视频候选组索引
- n: 已使用 GPU 数

转移: dp[g][n] = max(dp[g-1][n-k] + score(candidate_k))
```

**阶段 3: 回溯最优解**
- 对剩余免费 GPU 查找最佳图像候选
- 选择全局最优方案

#### 4.3.3 求解开销

| 指标 | 结果 |
|------|------|
| DP 求解时间 (均值) | 0.30-0.41ms |
| DP 求解时间 (最大) | 1.9ms |
| 求解器开销/步骤 | < 0.25% (720p 基准 781ms) |

## 五、实验结果

### 5.1 实验设置

| 项目 | 配置 |
|------|------|
| 硬件 | 8× NVIDIA RTX PRO 6000 Blackwell (96GB GDDR7) |
| T2I 模型 | SD3.5 Medium (2.5B) |
| T2V 模型 | Wan2.2-T2V-5B (81帧) |
| 基准对比 | FCFS, SJF, SRTF, RASP |
| 主要指标 | SLO 达标率 (SAR) |
| 截止期 | σ × 1.5 × 离线延迟 |

### 5.2 端到端性能

| 实验 | GenServe | 最强基线 | 改善 |
|------|----------|---------|------|
| SLO scale σ=1.0 | 78% SAR | SRTF 71% | +7pp |
| SLO scale σ=1.3 | 90% SAR | SRTF 83% | +7pp |
| 平衡混合负载 | 80% SAR | SRTF 73% | +7pp |
| 视频主导负载 | 41% SAR | SJF 33% | +8pp |
| 图像延迟 P90 | 5.8s | FCFS 18.0s | 3.1× |
| 视频中位延迟 | 52s | FCFS 89s | -41% |

**最高改善:** 视频主导混合负载下，相比 SRTF 提升 15 个百分点；视频 SAR 达 SRTF 的 2.3×。

### 5.3 消融实验

逐步添加组件的 SAR 变化（偏斜分辨率设置）：

| 配置 | 总体 SAR | 图像 SAR | 视频 SAR |
|------|---------|---------|---------|
| FCFS 基线 | 20% | 20% | 20% |
| +抢占 | 39% | 68% | 10% |
| +DP 求解器 | 58% | 94% | 22% |
| +SP 切换 (完整) | 63% | 94% | 32% |

**关键发现:** 无 DP 协调的抢占会损害视频性能（10%），DP 求解器贡献 +19pp 并同时提升两个模态的 SAR。

### 5.4 部署策略对比

复制式协同服务在所有混合负载下均优于静态 GPU 分区：

| 负载类型 | 复制式 | 最佳分区 | 改善 |
|---------|--------|---------|------|
| 视频主导 | 40% | 36% | +4pp |
| 平衡混合 | 72% | 64% | +8pp |
| 图像主导 | 96% | 92% | +4pp |

## 六、关键创新点

1. **首次提出扩散模型异构工作负载协同服务框架**
   - 利用扩散推理的可预测性和步骤边界可抢占性
   - 开辟了异构感知资源管理的新设计空间

2. **步骤级智能抢占机制**
   - 不同于 LLM 推理的不可预测输出长度
   - 扩散模型可精确估计每个请求的剩余成本
   - 实现零成本（<0.2%）的细粒度抢占

3. **弹性序列并行度与动态批处理的协调**
   - T2I 通过批处理提升 GPU 利用率
   - T2V 通过动态 SP 调整适应不同分辨率
   - 两种机制紧密耦合

4. **轻量级 DP 联合优化调度器**
   - 在每次调度轮次联合决定抢占、批处理和并行度
   - 全局最大化 SLO 满足率
   - 避免 MILP 求解器的秒级延迟

5. **复制式协同服务架构**
   - 所有 GPU 动态同时服务 T2I 和 T2V
   - 避免静态 GPU 分区导致的资源碎片化

## 八、局限性与未来工作

### 8.1 当前局限

1. **仅支持 T2I/T2V**: 未扩展到 I2V、TI2V 等更复杂的任务
2. **单模型假设**: 未考虑不同模型（如 SD3.5 vs FLUX）的混合
3. **静态帧数**: 未优化不同帧数视频的调度
4. **NPU 支持**: 论文仅在 NVIDIA GPU 上验证

### 8.2 未来方向

1. **扩展到更多任务**: I2V、TI2V、视频编辑等
2. **多模型调度**: 不同大小模型的混合调度
3. **NPU 适配**: 在 Ascend NPU 上验证和优化
4. **流式生成**: 结合 CausalWan 等流式模型的调度

## 十、总结

GenServe 通过暴露和利用扩散工作负载的结构特性（可预测性、步骤边界可抢占性），实现了异构工作负载的高效协同服务。其核心贡献是：

1. **首次系统化地解决了扩散模型异构工作负载的调度问题**
2. **提出了步骤级智能抢占机制，实现零成本细粒度抢占**
3. **设计了轻量级 DP 联合优化调度器，求解开销 < 0.25%**
4. **在真实硬件上验证，SLO 达标率最高提升 44%**

这篇论文对优化 Wan2.2 的在线服务调度很有参考价值，特别是：
- T2I/T2V 混合请求的调度
- SP 度数的动态调整
- 批处理与抢占的协调
