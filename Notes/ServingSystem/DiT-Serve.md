# DiT-Serve: An Efficient Serving Engine for Diffusion Transformers


---

## 一、问题背景

扩散 Transformer（DiTs）正在成为图像和视频生成的主流架构，但**服务 DiTs 既技术复杂又成本高昂**：

1. **自注意力的二次复杂度**：生成一个高分辨率视频往往需要数分钟
2. **请求高度异构**：用户的请求在以下维度上差异巨大：
   - 分辨率：240p–1080p
   - 去噪步数：20–120 步
   - 视频时长：2–60 秒

现有 LLM 服务系统（如 vLLM、SGLang）针对文本做了大量优化（连续批处理、分页注意力等），但**几乎没有针对扩散模型的跨请求优化**。

---

## 二、两个核心低效问题

### 2.1 时间维度的低效（Temporal Underutilization）

当不同去噪步数的请求被批处理在一起时，步数少的请求完成后 GPU 就空闲了，必须等待最长的请求完成。

> 例如：请求 A 需要 2 步，B 需要 6 步，C 需要 4 步
> → A 和 C 的 GPU 分别空闲 4 和 2 个时间单位

### 2.2 空间维度的低效（Spatial Underutilization）

当请求的分辨率或时长不同时，序列长度差异很大。现有的序列并行方案（如 Ring Attention）会将所有序列填充（padding）到最长长度，导致 GPU 计算和内存大量浪费。

> 例如：A、B、C 分别需要 8、4、2 个 GPU，但都被填充到 8 个 GPU
> → 50–75% 的容量被浪费在 padding 上

## 三、Ring Attention 详解（前置知识）

### 3.1 为什么需要 Ring Attention？

**核心矛盾：注意力需要看到所有 token，但一个 GPU 放不下。**

Self-attention 的本质：每个 token 都要和所有 token 做点积，得到注意力权重。

```
token 0 要看到: token 0, 1, 2, 3, ..., 999999
token 1 要看到: token 0, 1, 2, 3, ..., 999999
...
```

如果序列太长，一个 GPU 的显存放不下所有的 Q、K、V。

### 3.2 核心难点：softmax 不能直接分块算

普通的矩阵乘法可以分块再拼接，但 **softmax 不行**：

```
softmax([1, 2, 3]) = [e¹/(e¹+e²+e³), e²/(e¹+e²+e³), e³/(e¹+e²+e³)]

你不能先算 softmax([1,2]) 再算 softmax([3]) 然后拼起来
```

因为 softmax 的分母是**全局的**——需要所有元素才能算归一化常数。

### 3.3 解决方案：Online Softmax（在线 softmax）

数学上有一个技巧，可以**分块累积** softmax，核心是维护三个中间变量：

```
m_i：到目前为止见过的所有 QKᵀ 分数中的最大值（running max）
l_i：到目前为止的 exp(score - m) 之和（running sum）
O_i：到目前为止的部分输出（running output）
```

每收到一个新的 KV 块 `K_j, V_j`，更新规则如下：

```
1. 算局部分数：S_j = Q_i · K_jᵀ / √d

2. 更新最大值：m_new = max(m_old, max(S_j))

3. 用新最大值重新缩放旧的 sum 和 output：
   l_old_rescaled = l_old · exp(m_old - m_new)
   O_old_rescaled = O_old · exp(m_old - m_new)

4. 累加新块的贡献：
   l_new = l_old_rescaled + sum(exp(S_j - m_new))
   O_new = O_old_rescaled + exp(S_j - m_new) · V_j
   （最终输出时再除以 l_new 做归一化）
```

**关键：这个更新是"流式"的——你可以一块一块地接收 KV，逐步更新，最后得到正确的结果。**

### 3.4 Ring Attention 的执行过程（详细时序）

假设序列长度为 N，有 D=4 个 GPU。每个 GPU 持有序列的 1/4：

```
GPU 0: token [0 ~ N/4-1]     → Q₀, K₀, V₀
GPU 1: token [N/4 ~ N/2-1]   → Q₁, K₁, V₁
GPU 2: token [N/2 ~ 3N/4-1]  → Q₂, K₂, V₂
GPU 3: token [3N/4 ~ N-1]    → Q₃, K₃, V₃
```

#### 初始状态

```
GPU 0: Q₀, K₀, V₀, m₀=-∞, l₀=0, O₀=0
GPU 1: Q₁, K₁, V₁, m₁=-∞, l₁=0, O₁=0
GPU 2: Q₂, K₂, V₂, m₂=-∞, l₂=0, O₂=0
GPU 3: Q₃, K₃, V₃, m₃=-∞, l₃=0, O₃=0
```

每个 GPU 只有自己的 Q、K、V，中间变量（m, l, O）都初始化为零。

### 3.5 计算与通信的重叠（Pipeline）

这是 Ring Attention 的精髓。一个 GPU 在一个时间步内**同时做两件事**：

```
时间轴 →

GPU 0 第 0 轮：
  ┌─────────────────────────────────────────────┐
  │  ┌─────────────────────┐                     │
  │  │ 计算：Q₀ · K₀ᵀ/√d   │                     │  ← GPU 计算单元（SM）
  │  │ 更新 m₀, l₀, O₀     │                     │
  │  └─────────────────────┘                     │
  │  ┌─────────────────────┐                     │
  │  │ 发送 K₀,V₀ → GPU 1  │                     │  ← GPU 通信单元（NVLink）
  │  │ 接收 K₃,V₃ ← GPU 3  │                     │
  │  └─────────────────────┘                     │
  └─────────────────────────────────────────────┘
         ↑ 计算和通信同时进行！（不同硬件单元）

GPU 0 第 1 轮：
  ┌─────────────────────────────────────────────┐
  │  ┌─────────────────────┐                     │
  │  │ 计算：Q₀ · K₃ᵀ/√d   │ ← 用上一轮收到的 K₃ │
  │  │ 更新 m₀, l₀, O₀     │                     │
  │  └─────────────────────┘                     │
  │  ┌─────────────────────┐                     │
  │  │ 发送 K₃,V₃ → GPU 1  │                     │
  │  │ 接收 K₂,V₂ ← GPU 3  │                     │
  │  └─────────────────────┘                     │
  └─────────────────────────────────────────────┘
```

**为什么能重叠？**

- GPU 的**计算单元**（SM/流处理器）做矩阵乘法
- GPU 的**通信单元**（NVLink/网络接口）做数据传输
- 这是**不同的硬件**，可以同时工作
- 通信的数据量（一个 KV 块）远小于计算量（Q 乘以一个 KV 块），所以通信时间被计算时间完全掩盖

### 3.6 时序图：4 个 GPU 的完整流水线

```
时间 →  t₀        t₁        t₂        t₃

GPU 0:  [算K₀,发K₀] [算K₃,发K₃] [算K₂,发K₂] [算K₁,发K₁]
GPU 1:  [算K₁,发K₁] [算K₀,发K₀] [算K₃,发K₃] [算K₂,发K₂]
GPU 2:  [算K₂,发K₂] [算K₁,发K₁] [算K₀,发K₀] [算K₃,发K₃]
GPU 3:  [算K₃,发K₃] [算K₂,发K₂] [算K₁,发K₁] [算K₀,发K₀]

通信流向：
  t₀: GPU0→GPU1, GPU1→GPU2, GPU2→GPU3, GPU3→GPU0
  t₁: GPU3→GPU0, GPU0→GPU1, GPU1→GPU2, GPU2→GPU3
  t₂: GPU2→GPU3, GPU3→GPU0, GPU0→GPU1, GPU1→GPU2
  t₃: GPU1→GPU2, GPU2→GPU3, GPU3→GPU0, GPU0→GPU1
```

**关键观察：每个时间步，所有 4 个 GPU 都在同时计算 + 同时通信。没有任何 GPU 闲着。**

### 3.7 与朴素方案的对比

**朴素方案（不重叠）：**

```
时间 →  t₀          t₁          t₂          t₃

GPU 0:  [  先收集所有 K₀~K₃  ] [  再计算 Q₀·K_all  ]
GPU 1:  [  先收集所有 K₀~K₃  ] [  再计算 Q₁·K_all  ]
GPU 2:  [  先收集所有 K₀~K₃  ] [  再计算 Q₂·K_all  ]
GPU 3:  [  先收集所有 K₀~K₃  ] [  再计算 Q₃·K_all  ]

→ 先全部收集完，再开始计算。通信和计算串行，总时间 = 通信时间 + 计算时间
```

**Ring Attention（重叠）：**

```
时间 →  t₀        t₁        t₂        t₃

GPU 0:  [算+发]    [算+发]    [算+发]    [算+发]
GPU 1:  [算+发]    [算+发]    [算+发]    [算+发]
GPU 2:  [算+发]    [算+发]    [算+发]    [算+发]
GPU 3:  [算+发]    [算+发]    [算+发]    [算+发]

→ 每一步同时计算和通信。总时间 ≈ max(通信时间, 计算时间) × D
→ 如果计算时间 > 通信时间（通常如此），通信完全被隐藏！
```

### 3.8 Ring Attention 的问题

Ring Attention 假设所有请求长度差不多。当批处理中有长度差异很大的请求时，会把短请求**填充（padding）到最长请求的长度**：

```
4 GPU 环，请求 A 需要 4 GPU，B 和 C 各需要 2 GPU：

GPU 0: [A 的 chunk] [B 的 chunk + 填充] [C 的 chunk + 填充]
GPU 1: [A 的 chunk] [B 的 chunk + 填充] [C 的 chunk + 填充]
GPU 2: [A 的 chunk] [  全是填充，空转  ] [  全是填充，空转  ]
GPU 3: [A 的 chunk] [  全是填充，空转  ] [  全是填充，空转  ]
```

50%–75% 的 GPU 容量被浪费。这就是 Brick Attention 要解决的问题。

### 3.9 总结：Ring Attention 的三个关键

| 关键点 | 解释 |
|--------|------|
| **在线 softmax** | 通过维护 running max (m) 和 running sum (l)，可以分块累积 softmax，每收到一块 KV 就更新一次 |
| **环形传递** | KV 块沿 GPU 环传递，D 轮后每个 GPU 都"见过"所有 KV |
| **计算-通信重叠** | 每一轮中，GPU 同时做两件事：①用当前 KV 计算注意力 ②把 KV 传给下一个 GPU。利用 GPU 计算单元和通信单元是不同硬件，实现流水线化 |

## 四、DiT-Serve 的两大创新

### 4.1 Step-Level Batching（步级批处理）

**核心思想：** 借鉴 LLM 服务中的连续批处理，在**每个去噪步**就进行调度决策。

**机制：**

- 每个时间步结束后，调度器可以选择：
  - 将已完成的请求移出
  - 将新的高优先级请求注入
- 不同于现有系统把每个请求当作不可分割的任务运行到底

**效果：** 消除 GPU 空闲周期，最大化利用率。

```
(a) Naive Batching（传统方式）：
请求 A (2步): ██
请求 B (6步): ████████
请求 C (4步): ████
                 ↑ A 完成后 GPU 空闲，等待 B

(b) Step-Level Batching：
请求 A (2步): ██
请求 B (6步): ████████
请求 C (4步):   ████      ← A 完成后立即插入 C
请求 D (2步):       ██    ← C 完成后立即插入 D
```

### 4.2 Brick Attention（砖块注意力）

**核心思想：** 不要用一个大环装所有请求，而是为每个请求分配一个大小合适的环。

#### 4.2.1 工作原理

在同一个硬件集群上构建多个不同大小的环（如 1、2、4、8 GPU 的环），每个请求分配到与其上下文长度成正比的环。

```
Brick Attention（同样 4 个 GPU）：

请求 A（长序列）→ 分配到 4-GPU 环：GPU 0, 1, 2, 3
请求 B（短序列）→ 分配到 2-GPU 环：GPU 0, 1
请求 C（短序列）→ 分配到 2-GPU 环：GPU 2, 3
```

图示（对应论文 Figure 6b）：

```
GPU 0          GPU 1          GPU 2          GPU 3
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ Q₀  KV₀ │   │ Q₁  KV₁ │   │ Q₂  KV₂ │   │ Q₃  KV₃ │
│    A    │   │    A    │   │    A    │   │    A    │ ← 4-GPU 环
│ Q₀' KV₀'│   │ Q₁' KV₁'│   │ Q₂' KV₂'│   │ Q₃' KV₃'│
│    B    │   │    B    │   │    C    │   │    C    │ ← 两个 2-GPU 环
└─────────┘   └─────────┘   └─────────┘   └─────────┘
    ↕              ↕              ↕              ↕
  同一个 GPU 同时参与多个环的通信！
```

**关键点：一个 GPU 可以同时属于多个环。**

#### 4.2.2 算法流程（对应论文 Algorithm 1）

```python
# 输入：M 个长度不同的请求的张量列表 X，D 个 GPU 设备
# 输出：M 个请求的注意力输出

# Step 1: 按长度降序排列（长的先处理，方便装箱）
X.sort(descending)

# Step 2: 为每个请求计算"块大小"（需要几个 GPU）
for each sequence x in X:
    # block_size = 向上取整到最近的 2 的幂次
    block_size = 2^ceil(log2(x.length / Lmax))

    # Step 3: 把 Q, K, V 按 block_size 切分，分配到对应 GPU
    devices = [cur_len, ..., cur_len + block_size - 1]
    [Q_batch, K_batch, V_batch] = split(Q, K, V) across devices

    # Step 4: 累计 GPU 使用位置，满了就换下一批
    cur_len += block_size
    if cur_len == D:
        cur_len = 0  # 开始新的一轮装箱

# Step 5: 并行计算注意力（每个 GPU 独立处理自己的部分）
for each device i in parallel:
    # 收集该 GPU 参与的所有环的 KV
    KV = [(K_k, V_k) for k in all rings this GPU belongs to]

    # 对每个环的每个块，独立传递 KV 并计算注意力
    for each block j:
        for each ring k:
            send(KV_k)              # 发送给同环的下一个 GPU
            A_j = Attention(Q_i, KV)  # 计算注意力
            KV_k = recv(k)          # 从同环的上一个 GPU 接收

    # 合并该 GPU 上所有环的输出
    Y_i = Combine(all attention outputs A)

# Step 6: 拼接所有 GPU 的输出
Y = Concatenate(all Y_i)
```

#### 4.2.3 为什么限制为 2 的幂次？

1. **简化装箱算法**：只需考虑 1、2、4、8 等大小，组合空间有限
2. **保证性能可预测**：2 的幂次的通信模式更规整，便于流水线优化
3. 使用 **best-fit 装箱算法**最大化 GPU 利用率

#### 4.2.4 为什么叫 "Brick"（砖块）？

想象装箱问题：你有不同大小的物品（请求），要装进固定数量的箱子（GPU）。

- Ring Attention：把所有物品都切成最大尺寸再装 → 浪费空间
- Brick Attention：用不同大小的 "砖块" 拼接，每块砖的大小是 2 的幂次，紧密拼接在一起

## 五、SRPTF（最短剩余处理时间优先）

### 5.1 从 SJF 到 SRPTF

经典的**最短作业优先（SJF, Shortest Job First）**是排队论中的最优策略——先执行最短的任务，可以最小化平均完成时间。

但扩散模型的 "作业长度" 不是固定的——一个请求在执行过程中，**剩余工作量是动态变化的**。所以需要一个动态版本：**SRPTF（Shortest Remaining Processing Time First）**。

### 5.2 剩余工作量的定义

对于一个当前处于去噪步骤 t 的请求：

```
剩余工作量 L(req_t) = (T_total - t) × S(req_t)
```

其中：

- `T_total`：该请求总共需要的去噪步数（比如 80 步）
- `t`：当前已经完成的步数（比如已经做了 20 步）
- `S(req_t)`：当前步骤的序列长度（patch 数量）
- `(T_total - t)`：还剩多少步没做

**示例：**

```
请求 A：总步数 80，已做 20 步，序列长度 1000
  → 剩余工作量 = (80 - 20) × 1000 = 60,000

请求 B：总步数 40，已做 30 步，序列长度 500
  → 剩余工作量 = (40 - 30) × 500 = 5,000

请求 C：总步数 120，已做 0 步，序列长度 2000
  → 剩余工作量 = (120 - 0) × 2000 = 240,000
```

排序结果：B (5,000) < A (60,000) < C (240,000) → **B 优先执行**

### 5.3 SRPTF 的动态特性

**每次调度决策时都要重新计算剩余工作量：**

```
时间步 1:  A(剩余 60k), B(剩余 5k), C(剩余 240k)
           → 先执行 B

时间步 2:  A(剩余 59k), B(剩余 4.5k), C(剩余 238k)  [B 又做了一步]
           → 继续执行 B（仍然最短）

时间步 5:  A(剩余 56k), B(已完成!), C(剩余 232k)
           → B 完成了，执行 A

时间步 10: A(剩余 51k), C(剩余 226k)
           → 继续执行 A
```

### 5.4 与 FCFS 的对比

**FCFS（先来先服务）的问题——队头阻塞（Head-of-Line Blocking）：**

如果一个大请求（长视频、高分辨率）先进来，后面所有轻量请求都必须等待它完成，即使它们只需要很短时间。

**SRPTF 的优势——小请求可以 "插队"：**

- 降低**平均**完成时间
- 降低**尾部**延迟（P95、P99）
- 提高整体吞吐量（因为小请求快速释放资源）

### 5.5 SRPTF 与 Step-Level Batching 的配合

两者天然配合：

```
Step-Level Batching 的每个去噪步结束时：
  1. 某些请求完成了（比如 B 做完了所有步）
  2. 调用 SRPTF 重新计算所有剩余请求的优先级
  3. 选择剩余工作量最小的请求填充空出的 GPU 槽位
  4. 执行下一步
```

形成一个**持续的动态调度循环**：每一步都做最优决策。

### 5.6 为什么不用 SJF 而用 SRPTF？

SJF 在一开始就根据总工作量排序，之后不变。但扩散模型的请求有两个特点：

1. **序列长度可能随步骤变化**（某些模型在不同步骤处理不同分辨率）
2. **中途可能有新请求到达**——新来的请求可能比正在执行的请求更短

SRPTF 天然处理这两种情况：每一步都重新评估，始终选择当前剩余工作量最小的。

## 六、三个技术的协同关系

```
                    ┌─────────────────────────────────┐
                    │         DiT-Serve 调度器          │
                    │                                   │
                    │  每个去噪步结束时：                  │
                    │  1. SRPTF 重新排序剩余请求          │
                    │  2. 选出最高优先级的请求组合          │
                    │  3. 交给 Brick Attention 执行      │
                    └──────────────┬──────────────────┘
                                   │
                    ┌──────────────▼──────────────────┐
                    │        Brick Attention            │
                    │                                    │
                    │  根据请求长度分配 GPU 环：            │
                    │  长请求 → 大环（多 GPU）             │
                    │  短请求 → 小环（少 GPU）             │
                    │  装箱算法：best-fit + 2的幂次限制     │
                    └──────────────────────────────────┘
```

- **SRPTF 负责 "选谁"**：决定这一批执行哪些请求
- **Brick Attention 负责 "怎么跑"**：决定这些请求怎么分配到 GPU 上
- **Step-Level Batching 负责 "何时切换"**：每一步都可以换一批请求

三者配合，同时解决了时间和空间两个维度的低效问题。

|------|---------|

- Naive（无批处理 + Ring Attention + FCFS）
- Static Batch（静态批处理 + Ring Attention + FCFS）

## 九、核心贡献总结

1. **首个**将视频和图像生成作为服务跨用户应用集成的系统
2. 提出 **Step-Level Batching**：在每个去噪步抢占和交换请求，消除时间气泡

4. 系统易部署，无缝集成 FastAPI，支持多种现有模型

## 十、与相关工作的对比

**xDiT：** 最接近的工作，也解决 DiT 在多 GPU 集群上的低效问题。xDiT 使用 PipeFusion 和 CFG 并行，但**只优化单个请求的延迟**。DiT-Serve 则**优化跨请求的调度**，处理不同去噪步数、分辨率、时长的异构工作负载。

**LLM 服务系统（vLLM、SGLang）：** DiT-Serve 的创新深受 LLM 服务启发：

- Step-Level Batching ↔ 连续批处理（Continuous Batching）
- Brick Attention ↔ 分页注意力（Paged Attention）的内存管理思想
- SRPTF ↔ LLM 服务中的抢占式调度
