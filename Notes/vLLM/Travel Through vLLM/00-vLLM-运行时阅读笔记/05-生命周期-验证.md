## 11. 完成、abort、shutdown：资源如何走到终点

### 11.1 正常完成

正常完成的链路是：

```text
scheduler.update_from_output()
→ Request 变为 STOPPED/LENGTH/REPETITION 等 finished
→ _free_request()
   → aux connector / KV connector / EC connector request_finished
   → encoder cache free
   → finished_req_ids
   → 立即或延迟 free KV blocks
→ EngineCoreOutput 送给 OutputProcessor
→ detokenizer 产生 finished=True
→ frontend 请求/stream queue 结束
```

`_free_request()` 的顺序在 `scheduler.py:L3220-L3252` 有明确注释：connector 必须先看到 request state，encoder cache 才能释放；connector 可能返回 delay-free 标记。`_free_request_blocks()` 在 `L3267-L3284` 用 `last_sched_seq` 与 `processed_step_seq` 建立 GPU/connector fence。

### 11.2 用户 abort 与 stop-string abort

同步 `LLMEngine.abort_request()` 在 `llm_engine.py:L226-L229` 先清理 OutputProcessor，再把剩余内部 request IDs 送给 EngineCore。异步 `AsyncLLM.abort()` 在 `async_llm.py:L967-L978` 做同样的两阶段操作。

stop string 由 OutputProcessor 的 detokenizer 识别后返回 `reqs_to_abort`；异步 output handler 随即调用 `engine_core.abort_requests_async()`。这让“文本已经足够、无需再生成”尽快回到 scheduler，而不会依赖下一次自然采样。

### 11.3 shutdown

EngineCore shutdown 会清理 structured output、executor、scheduler、分布式资源，并解冻 GC（`core.py:L883-L899` 附近）。GPUModelRunner.shutdown() 在 `model_runner.py:L2552-L2605` 先 `torch.accelerator.synchronize()`，再清理 CUDA graphs、connector、KV tensors、encoder/model hooks、speculator、extensible KV cache，最后 `gc.collect()` 和 empty cache。同步点在这里是必要的：释放 Python 引用之前，设备上的工作必须已经完成。

## 13. 可复用的阅读模型

阅读 vLLM V1 的关键不是记住每个类，而是对每个运行时对象问四个问题：

| 对象 | 谁拥有它 | 何时创建/更新 | 何时才可释放 |
|---|---|---|---|
| `Request` | Scheduler | admission、schedule、output update | finished 且 connector/旧 step 不再使用 |
| `SchedulerOutput` | Scheduler → worker | 每次 schedule | worker 消费并完成该 step 后 |
| KV block | `KVCacheManager`/`BlockPool` | prefix hit 或 allocate slots | 越过 step/connector fence 后回 free queue |
| worker request state | `GPUModelRunner` | `add_requests/update_requests` | `finish_requests/free_states` |
| `Future` / `AsyncOutput` | Executor / model runner | non-block execute | `result()`/`get_output()` 消费后 |
| frontend `RequestState` | OutputProcessor | add request | finished output 或 abort |
| per-request async queue | AsyncLLM / OutputProcessor | `generate()` 开始 | `q.close()` 且 finished/aborted |

一旦把 **logical frontier、physical block、device stream、transport queue、frontend stream** 分开，vLLM 中看似复杂的 prefill/decode、speculation、PP、DP、P/D 和 offload 路径都可以归结为同一件事：scheduler 产生一个有版本的执行计划，worker 在设备上提交并异步完成它，output path 再把完成结果映射回请求状态，同时只在所有消费者越过 fence 后复用物理资源。
