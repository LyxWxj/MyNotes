## 2. 初始化：配置如何变成可运行的 EngineCore

### 2.1 前端组装

`LLM.from_engine_args()` 在 `vllm/entrypoints/llm.py:L394-L397` 接收 `EngineArgs` 并构造 `LLM`。`LLM.generate()` 在 `L431-L495` 做 runner 类型检查、补默认 sampling 参数，然后进入 completion 请求路径；`enqueue()` 在 `L497-L545` 只入队，后续由 `wait_for_completion()` 驱动处理。源码文档明确说批量 prompts 会由引擎按内存约束自动 batching，并保留输入顺序。

`LLMEngine.from_engine_args()` 在 `vllm/v1/engine/llm_engine.py:L180-L200` 创建 `VllmConfig`，调用 `Executor.get_class()` 选择执行后端，再决定是否启用 V1 multiprocessing。`LLMEngine.__init__()` 在 `L57-L156` 完成三件事：

- 建立 data-parallel group（需要时）；
- 建立 `Renderer`、`InputProcessor` 和 `OutputProcessor`；
- 通过 `EngineCoreClient.make_client()` 选择 in-process、同步多进程或异步多进程 client。

这里已经出现一个重要的 ownership 边界：`InputProcessor` 负责把 `EngineInput` 变成 engine-core 可消费的 `EngineCoreRequest`；`OutputProcessor` 只负责 frontend request state 和最终用户输出，不参与 GPU scheduling。

`AsyncLLM.__init__()` 在 `vllm/v1/engine/async_llm.py:L94-L230` 使用 `EngineCoreClient.make_async_mp_client()`，并在已有 event loop 时立即启动 output handler。异步 raw prompt 的 tokenization/multimodal preprocessing 通过 `InputProcessor.process_inputs_async` 放到 renderer 线程池，避免阻塞 asyncio loop（`input_processor.py:L79-L84`，`async_llm.py:L471-L528`）。

### 2.2 EngineCore 初始化顺序

`EngineCore.__init__()` 位于 `vllm/v1/engine/core.py:L131-L287`：

```text
加载 general plugins
    ↓
创建 Executor / model executor
    ↓
_executor._initialize_kv_caches()
    ├── worker 提供 layer/KV layout
    ├── profile model run，估算可用 GPU memory
    └── 得到 KVCacheConfig 与 block 数量
    ↓
StructuredOutputManager
    ↓
Scheduler（block size、hash block size、KV/EC connector）
    ↓
初始化 prefix-hash、batch queue、speculative 标记、GC/env cache
```

源码事实：EngineCore 在 KV 初始化失败时会先 shutdown executor（`core.py:L171-L187`）；没有 KV group 时会关闭 chunked prefill（`L193-L198`）；当 `max_concurrent_batches > 1` 时创建 batch queue，用于 overlap scheduling/execution，并为 pipeline parallelism 减少 bubble（`L228-L240`）。启用 prefix cache 或 KV connector 时，engine 还会建立 `PrefixHashConfig`，使 frontend 能预先计算 prompt block hashes（`L245-L264`）。

KV memory 的精确容量不在 scheduler 中决定，而由 worker 的 profiling 得出。`vllm/v1/worker/gpu_worker.py:L724-L892` 的 `determine_available_memory()` 结合权重占用、profile run 和 CUDA graph 额外占用计算 `available_kv_cache_memory_bytes`；随后 worker 初始化 KV tensor，scheduler 只接收已经确定的 block 配置。这里的推断是：**scheduler 的“能否 admission”取决于 worker 初始化阶段测出的物理容量，而不是仅由 `max_num_batched_tokens` 决定。**

### 2.3 执行后端与进程边界

`vllm/v1/executor/abstract.py:L55-L150` 负责按 `distributed_executor_backend` 选择 `UniProcExecutor`、multiprocessing、Ray、external launcher 等 executor。`Executor.execute_model()` 在 `L279-L316` 通过 `collective_rpc("execute_model", scheduler_output, non_block)` 把同一个 `SchedulerOutput` 分发到 worker；非阻塞调用返回 future。

单进程 executor 的实现位于 `vllm/v1/executor/uniproc_executor.py:L32-L145`。`AsyncOutputFuture` 会在真正需要结果时调用异步 model runner output 的 `get_output()`；`non_block=True` 时 `UniProcExecutor` 返回这个 future。多进程 client 则把 client/frontend 与 EngineCore 分开，使用 ZMQ 传输 request/output；这只是进程间 transport 边界，模型 forward 仍由 EngineCore 中的 executor/worker 完成。

## 3. 请求准入：从 prompt 到 waiting queue

### 3.1 输入规范化

`InputProcessor` 定义在 `vllm/v1/engine/input_processor.py:L41-L84`，核心 `process_inputs()` 在 `L367` 起。它验证 sampling/pooling、LoRA、DP rank、模型输入和 multimodal 数据，然后生成 `EngineCoreRequest`。raw prompt 会经过 renderer tokenization；已经渲染好的 `EngineInput` 可以跳过重复预处理。请求 ID 会保留外部 ID，同时在默认配置下附加随机后缀，避免同一个外部 ID 在内部冲突（`input_processor.py` 的 `assign_request_id()`）。

`LLMEngine.add_request()` 位于 `vllm/v1/engine/llm_engine.py:L231-L321`：

1. 处理 `EngineCoreRequest` 或调用 `InputProcessor.process_inputs()`；
2. 注册 LoRA、应用 watermark、分配内部 request ID；
3. 先把 request 放入 `OutputProcessor`，再通过 `EngineCoreClient` 送进 core；
4. 当 `n > 1` 时创建 parent request，并为每个 child 建立独立的 core/frontend 状态。

同步 `LLMEngine.step()` 在 `llm_engine.py:L323-L376` 先拉取 `EngineCoreOutputs`，再交给 `OutputProcessor.process_outputs()`；DP 场景下，如果其他 rank 仍有工作，会设置 dummy batch 标记以保持集体通信对齐。

### 3.2 异步请求与取消

`AsyncLLM.add_request()` 在 `vllm/v1/engine/async_llm.py:L411-L560` 支持三类输入：已经存在的 `EngineCoreRequest`、渲染好的 `EngineInput`、需要在线程池预处理的 raw prompt；也支持 `AsyncGenerator[StreamingInput]`。它为每个请求创建 `RequestOutputCollector`，并把 request 加入 OutputProcessor 与 EngineCore。

`AsyncLLM.generate()` 的源码文档（`async_llm.py:L740-L784`）把路径写得很清楚：

```text
创建 per-request async stream
→ 处理输入
→ 把 request 放进 detokenizer/output processor
→ 把 request 放进独立的 EngineCore 进程
→ 后台 output_handler 从 EngineCore 拉结果
→ generate() 从本请求 queue 取结果并 yield
```

取消和错误不是只关闭 Python generator。`generate()` 在 `L818-L868` 对 `CancelledError`、`GeneratorExit`、验证错误和普通异常都调用 `await self.abort(..., internal=True)`，最后关闭 queue。也就是说，**客户端断开会沿着 frontend → OutputProcessor → EngineCore → Scheduler 的路径清理，而不是等待请求自然结束。**
