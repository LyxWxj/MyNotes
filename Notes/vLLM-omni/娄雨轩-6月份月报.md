# 月报：vllm-omni 分离式推理与 DAG Parallel 开发

**时间**：2026年6月
**项目**：vllm-omni Disaggregated DiT Inference & DAG Parallel
**分支**：feat-disaggregated-dit-inference（基于 vllm-omni main）

## 一、工作概述

本月主要工作围绕 vllm-omni 的分离式推理系统展开，目标是支持 diffusion pipeline 的多 stage 分离部署，以及 DAG 拓扑的请求路由。主要贡献包括：

1. 扩展 `SupportsComponentDiscovery` 协议，支持细粒度组件注册
2. 修改 Orchestrator 支持 DAG 拓扑（fan-in/fan-out）
3. 为 Wan2.2 I2V 模型实现双编码器 DAG 分离
4. 解决多个 stage 分离相关的技术问题

---

## 二、已完成的工作

### 2.1 Orchestrator DAG 拓扑支持

**问题**：Orchestrator 硬编码 `next_logical = src_stage_id + 1`，只能支持线性链路由，无法支持 DAG 拓扑。

**解决方案**：

1. **StagePool 添加 `input_sources`**：每个 stage 声明其依赖的前驱 stage
2. **Orchestrator 构建 successor 映射**：从 `input_sources` 自动构建 DAG 拓扑
3. **`OrchestratorRequestState` 添加 `pending_outputs`**：缓冲已完成 stage 的输出，支持 fan-in
4. **`_forward_to_next_stage` 改为 DAG 遍历**：遍历所有 successor，检查 fan-in 就绪状态
5. **`_next_stage_already_submitted` 支持 DAG**：检查所有 successor 是否已提交
6. **`_route_output` 改用 `has_successors` 判断**：替代原来的线性链判断

**测试结果**：在 QwenImage 3-stage 配置上测试通过，请求可以正确路由到各个 stage。

### 2.2 SupportsComponentDiscovery 协议扩展

**问题**：每个模型需要定义 `_STAGE_COMPONENTS` 字典，无法复用。

**解决方案**：

扩展 `SupportsComponentDiscovery` 协议，支持两种声明方式：

1. **粗粒度**（向后兼容）：`_encoder_modules`、`_dit_modules`、`_vae_modules`
2. **细粒度**（新增）：`_component_registry` + `_default_stage_layout`

新增 `get_stage_components(stage)` classmethod，自动推导每个 stage 需要的组件。

**实现示例**：

```python
class QwenImagePipeline(..., SupportsComponentDiscovery):
    _component_registry = {
        "text_encoder":  {"tokenizer", "text_encoder"},
        "transformer":   {"transformer"},
        "scheduler":     {"scheduler"},
        "vae_decoder":   {"vae"},
    }
    _default_stage_layout = {
        "encode":  ["text_encoder", "scheduler"],
        "denoise": ["transformer", "scheduler"],
        "decode":  ["vae_decoder"],
    }
```

### 2.3 Wan2.2 I2V 双编码器 DAG 实现

**目标**：为 Wan2.2 I2V 模型实现双编码器 DAG 分离，支持 TextEncoder 和 VAE Encoder 并行执行。

**实现内容**：

1. **修改 `Wan22I2VPipeline`**：
   - 添加 `SupportsComponentDiscovery` 继承
   - 定义 `_component_registry` 和 `_default_stage_layout`
   - 修改 `__init__` 支持 stage 感知加载
   - 添加 `execute_encode_text()` 和 `execute_encode_image()` 方法
   - 添加 `build_dummy_run_request()` classmethod

2. **创建 VAE Encoder 包装器**：
   - `VAEEncoderWrapper`：只加载 VAE encoder 部分，节省显存
   - 支持 `encode_image` stage 只加载 VAE encoder

3. **创建 DAG 配置 YAML**：
   - `wan22_i2v_dag.yaml`：4-stage DAG 配置
   - Stage 0 (encode_text) + Stage 1 (encode_image) → Stage 2 (denoise) → Stage 3 (decode)

4. **创建 stage input processor**：
   - `wan22_i2v.py`：`encode_to_denoise()` 和 `denoise_to_decode()` 函数
   - 支持 TI2V-5B 模式的 VAE encoder 输出

**DAG 拓扑**：
```
Stage 0 (encode_text): TextEncoder + Scheduler
    ↓
    ├→ Stage 1 (encode_image): VAE Encoder
    ↓
Stage 2 (denoise): Transformer + Scheduler  ← fan-in
    ↓
Stage 3 (decode): VAE Decoder
```

### 2.4 问题修复

| 问题 | 解决方案 |
|---|---|
| Weight Loader 检查失败 | 设置 `weights_loaded_by_model_init` 标志 |
| 模型注册表名称不匹配 | 使用注册表 key 而非类名 |
| transformer_2 误加载 | 检查值是否为 null |
| Decoder 热身问题 | `DiffusionSubmoduleRunner._warmup()` |
| Denoise 热身问题 | `build_dummy_run_request()` + 虚拟 tensor |

## 三、进行中的工作

### 3.1 Denoise 热身问题

**问题**：denoise stage 使用完整 `DiffusionEngine`，其 `_dummy_run()` 尝试运行完整 pipeline，但 disaggregated 模式下 `vae`、`text_encoder` 等组件是 None。

**当前方案**：在 pipeline 中实现 `build_dummy_run_request()` classmethod，返回预构建的虚拟 tensor。

**问题**：
- 每个模型都需要自己实现 `build_dummy_run_request()`
- 需要构造虚拟 tensor，逻辑复杂且容易出错
- 热身逻辑与业务逻辑耦合

**理想方案**：在 Orchestrator 层统一热身，但修改 Orchestrator 风险较高。

### 3.2 Wan2.2 I2V 测试

Wan2.2 I2V DAG 配置已创建，但尚未完成端到端测试。主要问题：
- Denoise 热身问题尚未完全解决
- 需要验证双编码器并行执行的正确性

## 四、技术难点与思考

### 4.1 Orchestrator 改动的风险

Orchestrator 是所有模型共享的核心调度器，改动可能影响所有模型的行为。线性链的假设渗透在很多地方（`_forward_to_next_stage`、`_next_stage_already_submitted`、`_route_output`），修改需要非常谨慎。

### 4.2 组件分离与热身的矛盾

组件分离（disaggregated inference）需要每个 stage 只加载需要的组件，但热身（warmup）需要完整的 pipeline 上下文。这是一个根本性的矛盾：

- **组件分离**：每个 stage 只加载需要的组件，节省显存
- **热身**：需要完整的 pipeline 上下文，避免第一次请求延迟

当前的解决方案是在 pipeline 层实现 `build_dummy_run_request()`，但这不是一个好的设计。

### 4.3 热身设计的思考

理想的热身方案应该在更高层次的调度器上进行（Orchestrator 或 StagePool 层），这样：
- 不需要知道模型内部结构
- 不需要构造虚拟 tensor
- 可以统一处理所有模型
- 热身逻辑与业务逻辑分离

但这需要修改 Orchestrator，风险较高。

## 七、总结

本月完成了 vllm-omni 分离式推理系统的核心架构改进：

1. **Orchestrator DAG 支持**：从线性链改为 DAG 拓扑，支持 fan-in/fan-out
2. **组件发现协议扩展**：支持细粒度组件注册，可复用于 offload 和 stage 分离
3. **Wan2.2 I2V 双编码器 DAG**：实现了第一个真正的 DAG 分离案例

主要未解决的问题是 Denoise 热身，需要在 Orchestrator 层统一处理。下一步将重点解决这个问题，并将 DAG 分离机制推广到更多模型。
